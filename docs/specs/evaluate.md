# evaluate

Files: `src/evaluate/evaluate.py` (command line, checks, writing) and `src/evaluate/metrics.py` (`compute()` and the metric maths). Both are assessment files.

## Purpose

The [`evaluate`](../definitions.md#workflows) workflow. Re-validate every raw record of one experiment under one release, and compute the [metrics](../definitions.md#metrics). No AI model takes part, and it never edits raw records. Running it twice gives the same output.

## Inputs

1. `--experiment ID`. Reads `results/<ID>/experiment.toml` and every file in `results/<ID>/raw/`.
2. `--release VERSION`, default the release in the experiment config. It must be that release or a [mirror](../definitions.md#releases-and-experiments) of it: same major and minor, the same `inputs.jsonl` hash, and the same `prompt_versions`, and the same `decision_prompt_versions` when both releases hold it. For example, an experiment run on `1.1.0` can be scored under `1.1.1`, never under `1.2.0`.
3. The assessment files in the checkout must hash to that release's `assessment_sha256`, and the checkout must render exactly the prompt versions the release froze (the same checks [run](run.md) makes). To score under an older release, check out its tag first.
4. Token prices. On the first evaluate of an experiment, `config/prices.toml` is copied to `results/<ID>/prices.toml`. Every later evaluate reads the copy, so a price change never rewrites a committed report. To use new prices, delete the copy on purpose.
5. Every AI model in the experiment config needs a price in the prices file, whether or not it has records. The check is `check_prices` in `src/run/budget.py`, shared with `run`; `evaluate` reports its message as an error. With `batch = true`, it also needs the [batch prices](../definitions.md#prices) of every AI model that goes through a [batch](../definitions.md#batches). Whatever the config says, a model with any record whose `batch` is true needs them too, else `evaluate` fails with `<prices file>: model '<name>' has batch records but no batch prices`.
6. Raw files are read with the shared `read_raw` helper from [run](run.md) (`src/run/raw.py`, an assessment file): a line that does not parse as a JSON object is skipped and counted, and the count goes to the report as `Torn raw lines skipped`. A record that lacks a required field is a checked error that names the file. A repeated (input id, setup, AI model, attempt number) is also a checked error that names the file.
7. Optional `--releases`, `--results`, and `--prices` paths, for tests.

`evaluate` exits with code 1 and writes nothing if any check fails.

## Outputs

1. `compute(raw_records, release_dir, prices, models=None, decision_models=frozenset()) -> (attempt_rows, metric_rows, summary_rows)`. `models` is the list of AI model names in config order, used to sort the rows; it defaults to the names found in the records.
   `evaluate` builds `decision_models` from the experiment config: the names of the AI models whose provider is a decision provider. `compute` decides each record with `is_decision_record(record, decision_models)`: the record's own `decision` field when it has one, else whether its AI model is in `decision_models`. It passes the result to the [validator](validator.md#decision-path), so decision raw responses are read as arrays of calls. It also passes the offered [mismatch reasons](../definitions.md#attempts-and-outcomes), `offered_reasons(engine)` from the [validator](validator.md), when the release's manifest has `mismatch_reasons` true, and `None` otherwise. `REQUIRED` fields in `read_raw_dir` do not include `decision` or `requested_model`, because older records lack them.
   1. `attempt_rows` has one row per raw record: its identifying fields, the outcome from re-validation, and the outcome stored in the raw record. Each row also carries `impossible_move`, `mismatch_reason`, and `decoy` from re-validation, its input's `corruption`, and `answer_class` from `answer_class(row)`: `tp`, `fp`, `tn`, `fn`, or `None` for an attempt that isn't a [classified answer](../definitions.md#attempts-and-outcomes). An attempt claims the puzzle can't be solved when its `mismatch` flag is on or it has no parsed moves, and claims a solution otherwise. `tp` claims a solution and has outcome `success`. `fp` claims a solution and has any other classified outcome. `tn` claims it can't be solved, on an invalid input, with the `mismatch` flag on and, under a release with mismatch reasons, a `mismatch_reason` equal to the input's corruption type. Without mismatch reasons the prompt asked for no reason, so a flagged invalid input is `tn`. `fn` is any other classified answer that claims it can't be solved, so a decision model that moves and then picks a mismatch option is `tn` or `fn`, never `tp` or `fp`. Each row also carries `reasons`, whether the release offers mismatch reasons.
   2. `metric_rows` has one row per puzzle, setup, AI model, scramble depth, and validity label, with these columns:
      1. `attempts` and `infrastructure_failure_count`.
      2. `precision`, `coverage`, `hallucination_rate`, `mismatch_detection_rate` (invalid rows only), `false_mismatch_rate` (valid rows only), `malformed_output_rate`, `truncated_rate`, `abstention_rate`, `format_error_rate`, `reason_hallucination_rate`, and `diagnosis_rate` (invalid rows only). `precision` counts `tp` and `tn` as hits over the attempts with an `answer_class`, and `coverage` counts the attempts with an `answer_class` as hits over all of them. `hallucination_rate` counts an attempt with `impossible_move` as a hit, and only the attempts that gave moves (`gave_moves(row)` in `metrics.py`: `parsed_moves` is not empty), so `_n` and `_inputs` cover those attempts and the inputs that have one. It is `n/a` with `_n` 0 when no attempt gave moves, and for a group whose attempts all come from a [decision model](../definitions.md#setups), read from each attempt row's `decision` value (the raw record's `decision`, or the config rule for an old record). `reason_hallucination_rate` counts an attempt with `decoy` as a hit, over the attempts with a `mismatch_reason`, decision-model attempts included. `diagnosis_rate` counts an attempt as a hit when its mismatch flag is on and its `mismatch_reason` equals `corruption_type(corruption)`. Both are `n/a` with `_n` 0 under a release without mismatch reasons, and `reason_hallucination_rate` also when no attempt has a reason. Each rate has four more columns: `<rate>_n`, the attempts behind it, `<rate>_inputs`, the inputs behind it, and `<rate>_low` and `<rate>_high`, its 95% bootstrap interval over inputs (see below).
      3. `consistency`, and `latency_per_attempt_s`, which leaves out [batched](../definitions.md#batches) attempts because their `latency_s` is `null`, and is n/a when every attempt in the row is batched.
      4. `input_tokens_per_attempt`, `output_tokens_per_attempt`, and `cost_per_attempt`, the mean [cost](../definitions.md#prices) per attempt with infrastructure failures included. `attempt_cost(raw, price)` prices a record at the batch prices when its `batch` is true, and at the standard prices otherwise, through `tier_prices(price, batch)` in `src/evaluate/metrics.py`. A record with no `batch` field is read as false. Each attempt row carries `batch`.
   3. `summary_rows`: the same rates and their intervals, pooled over puzzles and depths, with one row per AI model, setup, and validity label. Valid and invalid inputs are never pooled together.
2. `paired_tests(attempt_rows, models=None) -> paired_rows` in `metrics.py`: the [paired setup test](../definitions.md#metrics), pooled over scramble depths and never over validity labels, one row per AI model, puzzle, validity label, metric, and setup pair, with columns `model, puzzle, validity, metric, setup_a, setup_b, inputs_paired, a_higher, b_higher, mean_difference, p_value, p_holm, significant`.
   1. `models` is the list of AI model names in config order. It defaults to the names found in the rows, sorted, the same as `compute`.
   2. `metric` is one of `precision`, `hallucination_rate`, `mismatch_detection_rate` (invalid rows only), and `diagnosis_rate` (invalid rows only, and only under a release with mismatch reasons). A hit for `precision` is `tp` or `tn`, over the attempts with an `answer_class`, so an input with none under a setup is unpaired for that pair. A hit for `hallucination_rate` is an attempt with `impossible_move`. There are no `hallucination_rate` rows for a group whose attempts are all decision-model attempts. For `hallucination_rate`, `input_shares` also leaves out attempts that gave no moves, so an input with none under a setup has no share there and is unpaired for that pair.
   3. Setup pairs follow `SETUPS` order: (no_model, descriptive), (no_model, prescriptive), (descriptive, prescriptive).
   4. `mean_difference` is the mean over paired inputs of share_b − share_a.
   5. Rows are sorted by AI model (the order of `models`), puzzle, validity (valid first), metric (the order above), and pair.
   6. `significant` is `p_holm < 0.05`. When `inputs_paired` is 0, `mean_difference`, `p_value`, `p_holm`, and `significant` are `n/a`, and the row is left out of the Holm family.
   7. Holm: sort the family's p-values ascending. The adjusted p_(i) is the maximum over j ≤ i of min(1, (m − j + 1) × p_(j)), with m the family size.
3. `bootstrap_interval(cells, key) -> (rate, low, high)` in `metrics.py`: `cells` is one `(hits, attempts)` pair per input, sorted by input id. The rate is total hits over total attempts. Each of 2000 draws (`BOOTSTRAP_DRAWS`) picks as many inputs as there are, with replacement, and takes the rate over the picked cells. `low` and `high` are `sorted[int(0.025 * B)]` and `sorted[int(0.975 * B) - 1]` of the draw rates. The generator is `random.Random` seeded with the sha256 of `bootstrap-v1|<key>` (`BOOTSTRAP_SEED`), where `key` names the group and the metric (the group's key fields joined with `|`, then the rate name; summary rows start with `summary|`), so the result never depends on group order. The result is `n/a` three times for 0 attempts, and `(rate, n/a, n/a)` for fewer than 2 inputs. A rate whose every attempt is a hit, or none is, has `low` and `high` equal to the rate. `rates()` builds the cells once per rate from each group's rows. The [report CSV pooling in the UI](ui.md) has no per-input cells and keeps a Wilson score interval for display only, marked `*` (`wilson` in `ui/pooling.py`).
4. `detection_rows(attempt_rows, models=None) -> detection_rows` in `metrics.py`: [balanced accuracy](../definitions.md#metrics) of mismatch detection, one row per AI model, puzzle, and setup, pooled over scramble depths, with the columns of `DETECTION_COLUMNS`: `model, puzzle, setup`, then `detection_rate` and `false_mismatch_rate`, each with its `_low`, `_high`, `_n`, and `_inputs` columns from `rate_columns`, then `balanced_accuracy, balanced_accuracy_low, balanced_accuracy_high`, then `diagnosis_rate` with its four columns, then `critical_thinking, critical_thinking_low, critical_thinking_high`, then `fixed_answer_reason` and `fixed_answer_critical_thinking`, then `balanced_precision, balanced_precision_low, balanced_precision_high`, then `coverage` with its four columns, then `cost_efficiency`. The diagnosis and critical thinking columns are `n/a` under a release without mismatch reasons. These rows hold the headline metrics, because each of them combines both validity labels.
   1. Attempts with outcome `infrastructure_failure` are left out. Rows are sorted by AI model (the order of `models`), puzzle (registry order), and setup (`SETUPS` order).
   2. Detection is over invalid attempts, false mismatch over valid ones. Each rate has a bootstrap interval over inputs, key `<model>|<puzzle>|<setup>|<rate name>`. A rate is `n/a` when its n is 0, and balanced accuracy is `n/a` when either rate is.
   3. `balanced_accuracy_low` and `balanced_accuracy_high` come from `interval_for_balanced_accuracy(rows)`: a stratified bootstrap with the same draws and percentiles, where each draw picks valid and invalid inputs separately, each side as many as it has, and takes the balanced accuracy of the draw. The key is `<model>|<puzzle>|<setup>|balanced_accuracy`. It returns `n/a` for both when either side has fewer than 2 inputs. The [critical thinking](../definitions.md#metrics) interval uses the same function with the diagnosis hit on the invalid side, key `<model>|<puzzle>|<setup>|critical_thinking`. The [balanced precision](../definitions.md#metrics) interval uses it too, over the classified answers only, with a `tp` or `tn` as the hit on both sides, key `<model>|<puzzle>|<setup>|balanced_precision`; a draw where a side has no classified answer is left out of the percentiles, and the interval is `n/a` when either side has fewer than 2 inputs with a classified answer.
   4. `fixed_answer_reason` is the most common corruption type among the puzzle's invalid inputs that have attempts, ties broken by `CORRUPTION_TYPES` order, and `fixed_answer_critical_thinking` is half its share of those inputs: the critical thinking of always answering `MISMATCH` with that reason.
   5. `balanced_precision` is the mean of `precision` over valid and over invalid attempts, `n/a` when either is. `coverage` is over all attempts of the row, both labels, infrastructure failures left out. `cost_efficiency` is the mean cost per attempt, over every attempt of the row including infrastructure failures, divided by `balanced_precision × coverage`, and `n/a` when that product is 0 or `n/a`. `detection_rows` needs the costs, so it takes `attempt_rows` with their `cost` column.
5. `corruption_rows(attempt_rows, models=None)` in `metrics.py`, with `corruption_type(description)`, the first two words of a corruption description. One row per AI model, puzzle, setup, and corruption type over invalid attempts, with `detection_rate` (the share with the mismatch flag on) and `diagnosis_rate`, each with its `_n`, `_inputs`, `_low`, and `_high` columns from `rate_columns`, key `<model>|<puzzle>|<setup>|<type>|<rate name>`. `diagnosis_rate` is `n/a` under a release without mismatch reasons. Each attempt row carries its input's `corruption`, so no `inputs` argument is needed. Attempts with outcome `infrastructure_failure` are left out. Rows are sorted by AI model, puzzle, setup, and type (`twisted corner`, `flipped edge`, `flipped wing`, `swapped corners`, `swapped edges`, `recoloured sticker`).
6. `reason_rows(attempt_rows, models=None)` in `metrics.py`: which reason the AI model gave against which corruption was there. One row per AI model, puzzle, setup, `expected` (the input's corruption type, or `none` for a valid input), and `reason` (a mismatch reason, or `none` for an attempt without one), with `attempts`, the count. Attempts with outcome `infrastructure_failure` are left out. Rows are sorted by AI model, puzzle, setup, `expected` (`none` first, then corruption type order), and `reason` (`none` first, then offered order). No rows under a release without mismatch reasons.
7. `results/<ID>/<VERSION>.metrics.csv`: `metric_rows`, for analysis in other tools.
8. `results/<ID>/<VERSION>.paired.csv`: `paired_rows`, with the same CSV conventions as the metrics CSV, except that `p_value` and `p_holm` are written with 6 significant digits (`{:.6g}`), so a small p-value is not rounded to zero.
9. `results/<ID>/<VERSION>.detection.csv`: `detection_rows`, with the same CSV conventions as the metrics CSV.
10. `results/<ID>/<VERSION>.corruption.csv`: `corruption_rows`, with the same CSV conventions as the metrics CSV, and a header-only file when there are no rows.
11. `results/<ID>/<VERSION>.reasons.csv`: `reason_rows`, with the same CSV conventions as the metrics CSV, and a header-only file when there are no rows.
12. `results/<ID>/<VERSION>.md`: the experiment report, written by [report](report.md).

Every metric follows its definition in [definitions.md](../definitions.md#metrics), including which attempts each one leaves out. A metric with no data is `n/a`.

Cost is `(input_tokens + retry_input_tokens) × price_input_per_mtok / 1,000,000` plus the same for output tokens.

## How to test

1. A hand-built fixture of 12 raw records on 2x2 inputs, covering every outcome, gives metrics equal to values worked out by hand in the test file.
2. `bootstrap_interval` is deterministic, gives `(2/3, n/a, n/a)` for one input and `n/a` three times for none, gives (1.0, 1.0, 1.0) for ten all-hit inputs, and is wider for 10 all-or-nothing inputs of 3 attempts each than for 30 independent attempts with the same hit share.
3. Adding infrastructure failures to the fixture changes no rate, consistency, or latency, but changes `infrastructure_failure_count`, tokens per attempt, cost per attempt, and cost efficiency.
4. A group with no classified answer has `precision` `n/a`, and its `cost_efficiency` is `n/a`.
5. A raw record whose stored outcome differs from re-validation shows both outcomes in `attempt_rows`, and the metrics use the re-validated one.
6. Scoring an experiment from `1.1.0` under `1.2.0` exits with code 1. Scoring it under a mirror `1.1.1` works.
7. Assessment files that don't match the release make it exit with code 1.
8. After the first evaluate, editing `config/prices.toml` doesn't change the output. Deleting `results/<ID>/prices.toml` makes the next evaluate use the new prices.
9. A torn line in the middle of a raw file, including one that ends in `}`, is skipped and counted. A duplicated attempt makes `evaluate` exit with code 1 and write nothing.
10. A config model without a price makes it exit with code 1 and write nothing.
11. Raw files are byte-identical before and after `evaluate`, and two runs give byte-identical output.
12. Sign test: 8 against 2 discordant inputs gives p = 0.109375 (exact), 0 against 0 gives 1.0, and 10 against 0 gives 0.001953125.
13. Holm on (0.01, 0.04, 0.03) gives (0.03, 0.06, 0.06).
14. An input with attempts under only one setup, or only infrastructure failures under one setup, is not paired.
15. Two attempts on one input count as one paired input. Shares of 0.5 and 1.0 make one discordant input.
16. Valid inputs get no `mismatch_detection_rate` rows.
17. `detection_rows`: 4 valid inputs with 1 flagged and 4 invalid inputs with 3 flagged give balanced accuracy 0.75, and an always-`MISMATCH` group gives 0.5.
18. The balanced-accuracy interval is pinned to an exact (low, high) for 4 valid and 4 invalid inputs, is (1.0, 1.0) for 2 perfect inputs per side (an unstratified draw could leave a side empty), and is `n/a` when a side has fewer than 2 inputs.
19. `bootstrap_interval` is pinned to an exact (low, high) for a fixed cells list and key. Reproducibility relies on Python's `random.Random` seeding and `choices`, whose output for a given seed has been stable since Python 3.6.
20. `corruption_type` reads old descriptions, and `corruption_rows` splits two invalid inputs of different types into two rows.
21. An attempt with a legal move line and a decoy MISMATCH line is a hit for `reason_hallucination_rate` and not for `hallucination_rate`. An attempt with an impossible move is the reverse.
22. `diagnosis_rate`: 4 invalid inputs, 3 flagged, of which 2 with their corruption type and 1 with `other`, give 0.5, and the same group gives `critical_thinking` 0.75 beside 2 valid inputs with none flagged.
26. `answer_class`: on a valid input, solving moves are `tp`, legal unsolving moves and an impossible move are `fp`, and `MISMATCH twisted corner` is `fn`. On an invalid input, any moves are `fp`, `MISMATCH` with its corruption type is `tn`, and `MISMATCH other`, a wrong type, or the decoy are `fn`. A decision model's moves followed by a mismatch choice with the right reason on an invalid input are `tn`, with `other` or on a valid input `fn`. Under a release without mismatch reasons, a flagged invalid input is `tn`. Abstention, format error, truncated, malformed output, and infrastructure failure are `None`.
27. Precision 0.5 on valid inputs and 1.0 on invalid ones give `balanced_precision` 0.75. 4 attempts with 3 classified give `coverage` 0.75, and a mean cost of 0.01 per attempt then gives `cost_efficiency` 0.01 / (0.75 × 0.75).
23. A decision-model group under a release with mismatch reasons has `hallucination_rate` `n/a` and a numeric `reason_hallucination_rate`.
24. Under a release without mismatch reasons, the reason columns are `n/a`, `reason_rows` is empty, and every other column equals what it was before mismatch reasons existed.
25. `reason_rows` counts a false MISMATCH under `expected` `none` with its reason.
28. A record with `batch` true costs its tokens at the batch prices, one with `batch` false or no field at the standard prices, and a mix in one experiment sums each at its own tier. Its `latency_s` `null` is left out of `latency_per_attempt_s`. A batch record for a model with no batch prices makes `evaluate` fail naming the model.
