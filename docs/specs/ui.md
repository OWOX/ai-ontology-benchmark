# ui

Files: `ui/server.py`, `ui/app.py`, `ui/gitdata.py`, `ui/bundle.py`, `ui/puzzleinfo.py`, `ui/catalogue.py`, `ui/experiments.py`, `ui/forms.py`, `ui/branches.py`, `ui/expdata.py`, `ui/pooling.py`, `ui/jobs.py`, `ui/commit.py`, `ui/project.py`, `ui/secrets.py`, `ui/common.py`, `ui/tomlw.py`, `ui/replay.py`, `ui/benchmarks.py`, `ui/static/index.html`, `ui/static/theme.js`, `ui/static/router.js`, `ui/static/markdown.js`, `ui/static/cube.js`, `ui/static/progress.js`, `ui/static/progressview.js`, `ui/static/cubepanel.js`, `ui/static/terminal.js`, `ui/static/expmetrics.js`, `ui/static/pages/benchmarks.js`, `ui/static/pages/models.js`, `ui/static/pages/puzzles.js`, `ui/static/pages/inputs.js`, `ui/static/pages/experiments.js`, `ui/static/pages/experiment.js`, `ui/static/pages/new.js`, `ui/static/pages/about.js`, `ui/static/style.css`, `ui/start.sh`.

Start: `./ui/start.sh` changes to the repo root, creates `.venv` with `python3 -m venv` (3.11 or later) and runs `pip install -e '.[test]'` only when `.venv` is missing, then runs `python -m ui.server` with its arguments, adding `--port 7991` unless they include `--port`. Before that it stops any process listening on that port: SIGTERM first, so a UI server stops its jobs, then SIGKILL for whatever still listens after 5 seconds. Later updates go through the Install button.

## Purpose

A local web page for finding your way around what the project holds on GitHub, and for starting new [experiments](../definitions.md#releases-and-experiments). A left menu leads to the AI models, the puzzles, the experiments with their metrics, and the README, all for one [release](../definitions.md#releases-and-experiments) at a time. A New Experiment screen picks puzzles and AI models, sets the parameters, runs the experiment while showing every attempt, scores it, and opens a pull request with the results. The page starts the existing scripts as subprocesses. It adds no logic to them, and computes metrics only with `src.evaluate.metrics`.

The architecture rules are in [AGENTS.md](../../AGENTS.md#architecture):

1. Git is the only source of persistent data. Everything the page shows is read from git refs with `git show` and `git ls-tree`, never by listing the work tree. The one exception is an experiment with a live job in this server, which is read from its local branch `results/<id>`.
2. `ui/` holds code only.
3. The UI process writes only `./secrets/`. Experiment data reaches git through `run`, `evaluate`, and the [commit](#commit) step, which write to the branch `results/<id>`. `run` and `evaluate` still write `results/<id>/` in the work tree, as their own specs say. The UI never writes `config/experiments/<id>.toml`. It starts `run --config -` and passes the config on stdin ([run.md](run.md#inputs)).
4. One experiment is one branch, `results/<id>`.

The UI may run `release` (which calls `generate` for a major bump) on a branch other than `main`, and never runs `generate` on its own. It never edits anything in `releases/`, `prompts/`, or `results/<id>/raw/`, and never writes to `main`.

## Start

```
python -m ui.server [--port 8765] [--root .] [--lan | --no-lan] [--allow-host NAME]
```

`--lan` is the default. It binds to `0.0.0.0` and serves every peer address, but only a `Host` that is an IP literal (IPv4, or IPv6 in brackets) or a name given with `--allow-host NAME` (repeatable, compared case-insensitively and without a trailing dot), each with any port or none, or `localhost` with the server's port. A router proxy may send its IP or its name with no port, or with `:443` or `:80`, so these need no port match. Any other `Host` gets 403 with a message that echoes the header (at most 100 characters) and says to add the name with `--allow-host`. On start it prints the loopback URL, one URL for this machine's primary LAN address from a UDP probe (in any range, not only private ones), and the line "Open to every client: anyone who can reach this port can run experiments on your API keys (use --no-lan for this machine only)", preceded by the allowed host names when there are any. `--no-lan` binds to `127.0.0.1`, serves only peers in `127.0.0.0/8` and `Host` headers of `localhost:<port>` or `127.x.x.x:<port>`, and prints only the loopback URL. With `--no-lan`, a peer outside `127.0.0.0/8` is dropped before its request is read. An idle connection times out after 30 seconds. `--root` is the repo root, for tests. A restart binds at once, even while old connections are closing. It exits with code 1 if another server answers on `127.0.0.1:<port>` (checked before binding, because macOS lets a `0.0.0.0` and a `127.0.0.1` server share a port), or if `--root` has no `releases/` folder.

The server uses `http.server.ThreadingHTTPServer` with `daemon_threads = True`. Shared job state sits behind one `threading.Lock`.

On Ctrl-C or SIGTERM the server stops every live job the way `POST /api/stop` does (SIGINT, wait up to 10 seconds, then SIGTERM) before it exits, so no run outlives it.

The page polls. The server has no event stream.

## Inputs

Every path below is read from a git ref, never from the work tree, except the API keys, the live experiments in item 7, and the work-tree checks of API 2 (`local_results`, `local_report`), 8, 12, and 13.

1. Refs. `ui/gitdata.py` runs `git fetch --prune origin main '+refs/heads/results/*:refs/remotes/origin/results/*'` with `GIT_TERMINAL_PROMPT=0` and a 60-second timeout, at most once every 30 seconds, when a bundle is built with `refresh=1` or none is in memory yet. A failed fetch is not an error: the server builds from the refs it already has and reports `fetch_error` and the time of the last good fetch. `main` means `origin/main`, or `HEAD` when the repo has no `origin`.
2. Releases: the folders `releases/<version>/` on `main` with a `manifest.json`, newest first. For each, `manifest.json`, `inputs.jsonl`, and `prompts/<setup>/<puzzle>.txt`. The default release is the newest.
3. The model catalogue, `config/models.toml` on `main`, read by the UI only. Each entry has the same shape as a `[[models]]` entry in an experiment config, so the UI copies it unchanged:

   ```toml
   [[models]]
   name = "example-model"
   provider = "fake"
   api_model_id = "example-model-2026-01-01"
   kind = "system-2"
   params = { temperature = 1.0 }
   ```

   `kind` is `system-1` or `system-2` (see [definitions](../definitions.md#setups)). The UI copies it into the experiment config when the catalogue entry has one.

4. Token prices, `config/prices.toml` on `main`. A catalogue model with no price there is shown disabled with the reason "no price in config/prices.toml".
5. Puzzle descriptions, `docs/puzzles/<puzzle>.md` on `main`. The page shows the first paragraph after the title. A missing file shows "no description on main" and no link.
6. Experiments: each ref `origin/results/<id>`. From its tree: `results/<id>/experiment.toml`, every `results/<id>/raw/<model>.jsonl` (read with the same rules as `src.run.raw.read_raw`), and any `results/<id>/<version>.metrics.csv` and `results/<id>/<version>.md`. A branch with no `experiment.toml` is left out.
7. Live experiments: an id with a live job in this server is read from its local branch `refs/heads/results/<id>`, which `run` commits to after every record, and is marked `pushed: false` until the remote branch equals it.
8. The README, `README.md` on `main`.
9. The GitHub base URL, from `git remote get-url origin`, as `https://github.com/<owner>/<repo>`, accepting the `https://` and `git@github.com:` forms with or without `.git`. With no `origin`, or another host, every source link is left out.
10. API keys, one provider each for `src.run.models.KEY_VARIABLES`. A key is stored in `secrets/<provider>.json` as `{"api_key": "..."}`. The folder has mode 0700 and each file 0600, written atomically (a temp file in the folder, then replace). Saving overwrites the file and keeps no copy, and clearing deletes it. The server merges the saved keys under `os.environ`, so a real env var wins and the file is then ignored. An env var that is set but empty counts as unset. The merged env goes to subprocesses only. The page gets only whether a key is set, where it comes from (`env`, `file`, or `missing`), and its last 4 characters, never a whole key. Cloudflare also needs an account id (`ACCOUNT_VARIABLES`), stored in the same file as `{"api_key": "...", "account_id": "..."}`, and read from the env var `CLOUDFLARE_ACCOUNT_ID` first, like a key. The provider counts as configured only when both are set. The page gets only the account id's source, never any of its characters. A model whose provider key is missing is shown disabled with the reason "no API key: add it under Models", and a Cloudflare model whose token is set but whose account id is missing with "no account id: add it under Models". The `fake` and `fake_decision` providers need no key. There is no `.env` support. Terminal users export the variables themselves.

`run` and `evaluate` still read releases, prices, and the assessment from the work tree, as their specs say. A release that is on `main` but not in the work tree is offered by the page, and `run` then exits with its own error.

## Bundle

`ui/bundle.py` builds one JSON object per release with everything the menu pages show, so a page changes without another request:

```json
{"schema": 3, "release": "1.1.1", "releases": ["1.1.1", "1.1.0", "1.0.0"],
 "fetched_at": "2026-10-25T10:12:00Z", "fetch_error": null, "repo": "https://github.com/<owner>/<repo>",
 "main_sha": "<sha>",
 "defaults": {"attempts": 3, "retry_cap": 3, "max_output_tokens": 32000,
              "reasoning_effort": "medium",
              "budget": {"per_request_usd": 2.0, "per_model_usd": 25.0, "per_experiment_usd": 50.0}},
 "providers": [{"name": "anthropic", "variable": "ANTHROPIC_API_KEY", "key": {"source": "file", "tail": "ab12", "configured": true},
                "models": [{"name": "claude-opus-5-5", "api_model_id": "claude-opus-5-5", "kind": "system-2", "params": {},
                            "price": {"input_per_mtok": 5.0, "output_per_mtok": 25.0}, "disabled_reason": null,
                            "experiments": ["<id>"]}]}],
 "puzzles": [{"name": "2x2", "n": 2, "input_count": 60, "depths": [1, 3, 5], "valid": 40, "invalid": 20,
              "description": {"text": "...", "source": "<url>"},
              "prompts": {"no_model": {"text": "...", "version": "<12 hex>", "source": "<url>"}},
              "legal_moves": ["U", "U'"], "legal_moves_source": "<url>",
              "impossible_seen": [{"move": "u", "count": 3, "models": ["..."], "experiments": ["<id>"]}],
              "inputs_source": "<url>"}],
 "experiments": [{"id": "...", "model": "...", "provider": "...", "api_model_id": "...", "puzzle": "2x2", "validity": "all",
                  "release": "1.1.1", "started_at": "2026-11-04T12:30:00Z", "attempts": 180, "infrastructure_failures": 0,
                  "precision": 0.41, "hallucination_rate": 0.12, "mismatch_detection_rate": 0.6,
                  "false_mismatch_rate": 0.05, "malformed_output_rate": 0.0, "truncated_rate": 0.0, "abstention_rate": 0.0, "format_error_rate": 0.0,
                  "total_tokens": 812345, "cost_usd": 3.21, "metrics_source": "report",
                  "report_version": "1.1.1", "differs_from_catalogue": false, "served_models": ["..."],
                  "pushed": true, "running": false, "error": null, "branch": "<url>"}],
 "about": {"markdown": "...", "source": "<url>"},
 "metric_definitions": {"terms": {"Precision": "The share of attempts, ..."}, "source": "<url>#metrics"}}
```

1. `providers` come in the order anthropic, openai, google, typesafe, cloudflare, fake, fake_decision (`PROVIDER_ORDER`, then any other provider by name), each with its catalogue models in file order. A provider with no catalogue models is left out. Its `key` is `{"source", "tail", "configured"}`, plus `"account": {"variable", "source"}` for `cloudflare`. A model's `experiments` are the ids whose config holds an entry with the same `provider` and `api_model_id`, so experiments are matched on what was called, not on the name. `defaults` is the `DEFAULTS` dict of `ui/experiments.py`, the starting values of New Experiment.
2. `puzzles` are the release's `release_config.puzzles`. `n` is the side for an `NxN` name, else `null`. `prompts` hold the template for each setup with the placeholder `{state}` left in, and the prompt version from the manifest. `legal_moves` is the engine's `legal_moves()` from the registry. The page shows it and the server never sends a second copy anywhere else. A puzzle with no engine has `legal_moves: null`. `impossible_seen` lists every parsed move of every record of that puzzle in this release's experiments that is not in `legal_moves()` (exact string match), with its count, the AI models that returned it, and the experiment ids, sorted by count. It comes from the re-validated attempt rows (`parsed_moves` from the validator, not the stored value), validated as decision records by each record's `decision` field, or for a record without one by whether its AI model's provider is in `DECISION_PROVIDERS` in the experiment's config (`is_decision_record`, the same rule as the experiment rows), taken from the rows the build already scored for the experiment list and the scored cache, and is never written down. An experiment with a record that cannot be scored adds nothing. A stored `parsed_moves` that is not a list, or an entry that is not a string, is ignored, and an experiment that cannot be read adds nothing.
3. `experiments` has three rows per experiment, AI model, and puzzle, one for each `validity` scope: `all`, `valid`, and `invalid`, for the experiments of every release on `main`, because the Experiments page picks its releases itself. Every other part of the bundle reads only the experiments whose release is the bundle's release or one of its mirrors. Rates leave out `infrastructure_failure` attempts, as [definitions.md](../definitions.md#metrics) says, and are `null` with an empty denominator. `started_at` is the earliest `created_at` over the experiment's raw records, or `null` when it has none. `total_tokens` is input, output, retry input, and retry output tokens summed. `cost_usd` uses the prices in `results/<id>/prices.toml` on the branch when there is one, else `config/prices.toml` on `main`.
   1. When the branch has `results/<id>/<version>.metrics.csv` for the newest such version, the row's rates are pooled from its rows for that AI model, puzzle, and scope (each rate's numerator over its `_n`), and `metrics_source` is `report`.
   2. Otherwise the server computes them from the raw records with `src.evaluate.metrics.compute` under the experiment's release, for display only, and `metrics_source` is `computed`. Nothing is stored.
   3. `differs_from_catalogue` is true when the experiment's entry for the AI model differs from the catalogue entry with the same name in `api_model_id`, `provider`, or `params`, or the catalogue has no such name. `kind` is not compared, because experiments committed before the field existed have none.
   4. A branch whose config does not parse, or whose raw file has a record that lacks a required field, gives one row with `error` set to the message and every metric `null`. The other rows still build. Torn lines are skipped and counted, as in `evaluate`.
4. The server keeps built bundles in memory only, keyed by the release and the shas of `main` and of every `results/*` ref it read. The same shas return the same object. A moved ref rebuilds the bundle. Nothing is written to disk. The key status in `providers` and the disabled reasons that depend on it are not cached: they are filled in on every request, so saving a key shows at once.
5. A build is synchronous: the request waits until it is done.
6. `metric_definitions.terms` holds every numbered item under `## Metrics` in `docs/definitions.md` on `main`, keyed by its bold term without the full stop, as plain text: a link keeps its text and backticks are dropped. It is empty when the file or the section is missing. `source` links to that section, or is `null` with no GitHub base URL. The UI never keeps a second copy of a definition.

## Security

1. At start the server makes a token with `secrets.token_urlsafe(24)` and writes it into `index.html` as `<meta name="ui-token" content="...">`.
2. The default mode (`--lan`) has no network restriction: every peer address is accepted, so the server can sit behind a router's public name or proxy. It still checks `Host`, to stop DNS rebinding: a web page the owner visits can point its own hostname at this server and read the page and its token. A rebinding attack always uses a hostname, so IP literals and names passed with `--allow-host` (each with any port or none) and `localhost` (with the server's port) are the only accepted `Host` values.
3. Warning: in the default mode, anyone who can reach the port and sends an accepted `Host` gets the token, because the server puts it in the page it serves to every client that loads it. That client can start paid runs, use the saved API keys, and push. The traffic is plain HTTP, so anyone who can watch the network can read the token and any API key sent through the page. Use `--no-lan` to restrict the server to this machine. With `--no-lan`, every request from a peer outside `127.0.0.0/8` gets 403, and so does every request whose `Host` header is not `localhost:<port>` or `<ip>:<port>`, where `<ip>` is a literal address in `127.0.0.0/8`. An IPv4-mapped IPv6 peer counts as its IPv4 address. Hostnames are refused, which stops DNS rebinding.
4. Every `POST` without the header `X-Token: <token>` gets 403. So do `GET /api/commit/<id>` and `GET /api/bundle`, which can run `git fetch` and carry the key status, and `GET /api/secrets`.
5. Static files come from an allowlist: `/` serves `index.html`, and `/static/` serves exactly the files named under Files above. Any other path gets 404. Nothing outside `ui/static/` is ever served, so `secrets/` can't be reached.
6. A `POST` body is JSON of at most 64 KiB, or 400.

## HTTP API

Every JSON error is `{"error": "<message>"}` with a 4xx status. The message names the field at fault.

1. `GET /api/bundle?release=<version>&refresh=<0|1>` returns the [bundle](#bundle) for that release, default the newest. `refresh=1` fetches first, within the 30-second limit of Inputs 1. An unknown release gives 400 naming `release`.
2. `GET /api/experiments/<id>` returns one experiment in full, read from its branch as in Inputs 6 and 7:

   ```json
   {"id": "...", "release": "1.1.1", "config": {"...": "the form shape of item 5"},
    "model_entries": [{"name": "...", "provider": "...", "api_model_id": "...", "kind": "system-2", "params": {}}], "pushed": true, "running": false,
    "branch": "<url>", "metrics_source": "report", "local_results": true, "local_report": true, "report": {"version": "1.1.1", "markdown": "...", "source": "<url>"},
    "metric_rows": [], "summary_rows": [], "served_models": {"<model>": ["..."]}, "error": null}
   ```

   `metric_rows` and `summary_rows` are the columns of [evaluate](evaluate.md#outputs): from the newest report CSV on the branch when there is one (`summary_rows` then pooled from it by AI model, setup, and validity), else from `src.evaluate.metrics.compute`, with `metrics_source` `computed`. `report` is `null` when the branch has none. `model_entries` are the config's AI models with the `api_model_id`, `kind`, and `params` the experiment used (`kind` is `null` when the config has none), which the form leaves out. `local_results` is true when `results/<id>/experiment.toml` is in the work tree, one of two work-tree reads here (like API 12). `local_report` is true when `results/<id>/<config release>.md` is in the work tree (the report Commit requires), where `evaluate` writes it before it is committed (like API 13's age check). An unknown id gives 404.
3. `GET /api/inputs?release=<version>&puzzle=<name>` returns the release's inputs of that puzzle, in release order: `[{"input_id", "scramble_depth", "validity", "state", "scramble", "source_input_id", "corruption"}]`. An unknown release or puzzle gives 400 naming the field.
4. `GET /api/branches` returns every experiment branch, `[{"id", "release", "local": true, "remote": true}]`, sorted by id, for the New Experiment branch select. An id is listed when `results/<id>/experiment.toml` is on its local or remote branch.
5. `GET /api/experiment/<id>/config` returns the config on the experiment's branch (the local one first, else the remote one) as the form below, or 404. A config without `puzzles` returns every puzzle of its release.

   The form, which items 6 to 8 take:

   ```json
   {"id": "claude-opus-5-5-gpt-6-astra_2x2-3x3_20261025-1012", "release": "1.1.1", "puzzles": ["2x2"],
    "models": ["claude-opus-5-5"], "attempts": 3, "retry_cap": 3, "max_output_tokens": 32000, "reasoning_effort": "medium",
    "budget": {"per_request_usd": 2.0, "per_model_usd": 25.0, "per_experiment_usd": 50.0}}
   ```

   `reasoning_effort` is optional: `low`, `medium`, or `high`, written into the config the UI passes to `run` on stdin. A missing or null value leaves it out of the config, which is how an experiment saved without one resumes unchanged. Any other value gives 400. `models` holds catalogue names. A disabled model, an unknown release, or a puzzle that isn't in the release gives 400.
6. `POST /api/estimate {form}` and `POST /api/dry-run {form}` start `python -u -m src.run.run --experiment <id> --config - --estimate` and `... --dry-run`.
7. `POST /api/run {form, "limit": null, "parallel": 1}` starts one run job per model, all at once: `python -u -m src.run.run --experiment <id> --config - --model <name>`, plus `--limit N` if `limit` is set and `--parallel N` if `parallel` is above 1. `parallel` is absent or a whole number from 1 to 16, and anything else (0, 17, a boolean, a string) gives 400 naming `parallel`. It is not part of the experiment config, so it never changes the config text on stdin or the experiment's status, and estimate and dry-run ignore it. The server remembers it for each run job, for `parallel` in the snapshot (API 6). The processes can race to write `results/<id>/experiment.toml` because `run` writes it atomically ([run.md](run.md#outputs)). The response comes as soon as the jobs start, so the page can open the experiment's page at once. The branch step goes to the log as job `branch` of the id: "results/<id> exists: resuming" when `results/<id>` already exists, locally or on origin, else "creating results/<id>…", and then, from a watcher thread, "results/<id> created" once it exists. A new experiment's branch comes from `run`'s first commit, before any API call. A resumed one already exists. When every run job ends before any branch exists, the run failed before its first commit, and the watcher logs a `stderr` line, "run stopped before creating results/<id>: <the last stderr line>".
8. Items 6 and 7 build the experiment config from the form as TOML text with `ui/tomlw.py`, with `puzzles` always written, check it with `parse_experiment_config`, and pass it on each job's stdin. Nothing is written to disk. Before a job starts:
   1. The release must be in this checkout. The menu offers releases from `main`, but `run` reads `releases/<release>/` from the work tree, so a release missing there gives 409, "release <release> is on main but not in this checkout (releases/<release>/): merge main into the checked-out branch, then restart the UI". This check reads the work tree, like sub-item 7.
   2. For Run: a run job of the id alive gives 409, "a job of experiment <id> is running; stop it first", and so does a live evaluate job. Estimate and dry-run only read, so they refuse just while the same job of the id runs (API 22).
   3. No branch for the id: the experiment is new. Status `created`.
   4. A branch holds a config equal to the new one: status `unchanged`, and the run resumes. A model's `kind` is ignored when the saved entry for it has none, because experiments saved before the field existed have none. A missing `puzzles` counts as every puzzle of its release.
   5. A branch holds a config that differs only in `[budget]`: status `budget_updated`, and `run` replaces its copy.
   6. Any other difference: 409, "experiment <id> exists with a different config; load it or pick a new id".
   7. A branch exists but `results/<id>/experiment.toml` is missing from the work tree: 409, "the results of <id> are not in this checkout; check out its branch first". `run` appends to the raw files in the work tree, so resuming without them would run attempts the branch already holds. This check, like item 12's, reads the work tree.

   The response is `{"id", "status", "jobs": [...]}`.
9. The default id names the choice: the selected AI model names joined with `-`, then `_`, the selected puzzle names joined with `-`, then `_` and the local time as `YYYYMMDD-HHMM`. Every character outside `[A-Za-z0-9_-]` becomes `-`. With more than three AI models, the model part is `<count>-models`, and with more than three puzzles, the puzzle part is `<count>-puzzles`. It is `default_id(models, puzzles, now)` in `ui/experiments.py`, and the page asks the server for it with `GET /api/default-id?models=a,b&puzzles=2x2`.
10. `GET /api/state/<id>` returns the live snapshot, read from the experiment's branch as in Inputs 6 and 7:

    ```json
    {"id": "...", "release": "1.0.0", "setups": ["no_model", "descriptive", "prescriptive"],
     "attempts": 3, "models": ["example-model"],
     "inputs": [{"input_id": "2x2-d5-001", "puzzle": "2x2", "scramble_depth": 5,
                 "validity": "valid", "state": "RUUL..."}],
     "records": [{"model": "...", "input_id": "...", "setup": "...", "attempt_number": 1,
                  "outcome": "success", "mismatch": false, "created_at": "2026-11-02T21:09:49Z"}],
     "jobs": {"run:example-model": "running"},
     "parallel": {"example-model": 4},
     "report": "results/<id>/1.0.0.md"}
    ```

    `inputs` holds only the experiment's puzzles, in release order. `records` follows the rules of `src.run.raw.read_raw` over each model's raw file. `jobs` maps each job name of the id to its state. `parallel` maps each AI model with a running run job to the `--parallel` value that job was started with (API 7); a job started outside the UI, or before a server restart, counts as 1, and the map is empty when no run job is running. `report` is the report path if the branch has it, else `null`. The snapshot holds no in-progress attempt: the page works that out (see Polling). An unknown id gives 404.
11. `POST /api/stop {"id"}` sends SIGINT to every live run job of the id, waits up to 10 seconds, then sends SIGTERM to any still alive. A request that is in flight when the job stops may be paid for and never recorded, so the page says to prefer `limit` for small runs.
12. `POST /api/evaluate {"id", "release": null}` starts `python -u -m src.evaluate.evaluate --experiment <id>`, plus `--release <version>` if `release` is set (a bad version gives 400). 409 while a run job of the id is alive. `evaluate` reads `results/<id>/` from the work tree, so 409 "experiment <id> has no results in this checkout" when `results/<id>/experiment.toml` is missing there: that one check reads the work tree.
13. `GET /api/commit/<id>` returns the commit preview: `{"branch": "results/<id>", "base": "<sha>", "files": [...], "diffstat": "..."}`. 409 while any job of the id is alive, before the report exists, or when the report is older than any file in `results/<id>/raw/` (message "the report is older than the raw records; evaluate again first"). The age is the file modification times.
14. `POST /api/commit {"id"}` makes the commit and the pull request, and returns `{"branch": "...", "commit": "<sha>", "pr_url": "..."}`. The same 409 rules apply.
15. `GET /api/log?after=<seq>` returns the terminal lines newer than `seq` (default 0) and the job states:

    ```json
    {"lines": [{"seq": 41, "id": "t1", "job": "run:example-model", "stream": "stdout", "text": "..."}],
     "last": 41,
     "jobs": [{"id": "t1", "job": "run:example-model", "state": "running", "code": null}]}
    ```

    The server keeps one in-memory list of lines for all jobs, at most 5,000, dropping the oldest. `id` is the experiment id of the job that wrote the line, `""` for a project job, so two experiments that both run `run:<model>` stay apart. The page keys a failure banner by `(id, job)` and the ended-job check by `(id, job)`. `stream` is `cmd`, `stdout`, or `stderr`. The `cmd` line is the full command, logged before the process starts. `seq` counts up from 1 for the life of the server. `state` is `running`, `done`, `failed`, `budget`, or `stopped`. `budget` means the job exited 1 with a stderr line starting `error: budget reached:`. `stopped` means the UI stopped it.
16. `GET /api/secrets` returns `{"<provider>": {"variable": "ANTHROPIC_API_KEY", "configured": true, "tail": "ab12", "source": "env" | "file" | "missing", "location": "secrets/anthropic.json" | "env var ANTHROPIC_API_KEY" | null}}` for each provider. `POST /api/secrets {"provider", "action": "save" | "clear", "api_key", "account_id"}` saves a stripped key or deletes the file, and returns the same listing. `cloudflare` entries also carry `"account": {"variable": "CLOUDFLARE_ACCOUNT_ID", "source": "env" | "file" | "missing"}`, and its `configured` needs both values. `account_id` is optional and only for `cloudflare`, any other provider gives 400 naming `account_id`. Saving one field keeps the other, and clearing deletes the whole file, both fields. An empty key with no account id, or either with whitespace inside, gives 400 naming the field. Both need the token.

Project jobs belong to no experiment and use the id `""`. Their names are `install`, `tests`, `release`, and `push`. Each is echoed to the terminal like the others.

17. `GET /api/project` needs no token. It returns `{"branch", "clean", "latest_release", "python", "packages": {"anthropic": true, "openai": true, "google-genai": true, "pytest": true}, "gh": true}`. `branch` is `git rev-parse --abbrev-ref HEAD`, `clean` is true when `git status --porcelain` is empty, `latest_release` is `src.release.release.latest_version`, each package is checked with `importlib.util.find_spec` and never imported, and `gh` is whether the `gh` binary is found.
18. `POST /api/install` starts `python -u -m pip install -e .[test]`, with `.[test]` as one argument.
19. `POST /api/tests` starts `python -u -m pytest -q -p no:cacheprovider`.
20. `POST /api/release {"bump", "note"}` starts `python -u -m src.release.release --bump <bump> --note <note>`. A `bump` that is not `major`, `minor`, or `patch`, or a blank `note`, gives 400.
21. `POST /api/push` runs `git push -u origin <branch>`, then `git push origin <tag>...` for the `release-*` tags reachable from the branch (`git tag --merged <branch> --list 'release-*'`; skipped when there are none), then finds the open pull request with `gh pr view` or makes one with `gh pr create --base main --head <branch> --fill`, and returns `{"branch", "pr_url"}`. It adds no attribution. It runs inline, like commit.
22. Release and push give 409 when the branch is `main` or HEAD is detached. Install, release, and push give 409 while any job of any experiment, or any project job, is running, and while one of them runs every other job gives 409. Release also gives 409, naming up to 10 paths, when `git status --porcelain` is not empty. `tests` gives 409 only while the same job is running, and `dry-run` only while a dry run of the same id is.

23. `GET /api/replay/<id>?model=<name>&input_id=<id>&setup=<setup>&attempt=<n>` needs no token, like `/api/state`. It plays one attempt's moves on its input and returns every state on the way:

    ```json
    {"input_id": "2x2-d5-001", "puzzle": "2x2", "outcome": "hallucination", "moves": ["R", "U'", "X"],
     "frames": ["<state 0>", "<after move 1>", "<after move 2>"], "stopped_at": 2, "solved": false}
    ```

    The record is the one in `results/<id>/raw/<model>.jsonl` on the experiment's branch (Inputs 6 and 7), read with the rules of `src.run.raw.read_raw`, with that `input_id`, `setup`, and `attempt_number`. `moves` is its `parsed_moves`, empty for `malformed_output` and `infrastructure_failure`. `frames[0]` is the input's state from the experiment's release on `main`. Each next frame is the engine's `apply_move` of the next move. A move that is not in `legal_moves()` (exact string match) stops the replay: `stopped_at` is its index, and it and every later move get no frame. Otherwise `stopped_at` is `null`. `solved` is `is_solved` of the last frame when the replay did not stop and at least one move was applied, else false, and is for display only: `outcome` is always the record's own. A puzzle with no engine in the registry gives one frame. A missing or malformed `model`, `input_id`, `setup`, or `attempt` gives 400 naming the query field. An unknown experiment, a model outside the experiment, an unknown input, or no matching record gives 404. The move group is never sent to the page: the page only draws the frames.

24. `GET /api/attempt/<id>?model=<name>&input=<input id>&setup=<setup>&attempt=<n>` needs no token, like `/api/replay`. It returns what the experiment page's terminal shows for one attempt: `{"prompt": "<text>", "raw_response": "<text>" | null, "record": {...} | null}`. `record` is the raw record with that `input`, `setup`, and `attempt_number`, read as in `/api/replay` (Inputs 6 and 7), or `null` when it has not landed yet. `raw_response` is its raw response, or `null`. `prompt` is rebuilt from the experiment's release on `main`, never the work tree: the input from `releases/<release>/inputs.jsonl` and the template `releases/<release>/prompts/<setup>/<puzzle>.txt`, filled by `fill_template`. For a decision model (a provider in `DECISION_PROVIDERS`) it is `decision_state(prompt, [])`, then a line `--- questions`, then the questions JSON, as `run --dry-run` prints them. A missing or malformed `model`, `input`, `setup`, or `attempt` gives 400 naming the query field. An unknown experiment, a model outside the experiment, an unknown input, or a release without the template (or, for a decision model, the questions file) gives 404.

25. `GET /api/benchmarks?releases=<v,v>&models=<name,name>&puzzles=<name,name>&setups=<setup,setup>&validity=<all|valid|invalid>` returns the numbers of the [Benchmarks](#benchmarks) page. Every field is optional. `releases` defaults to the newest release with scored attempts from an experiment that ran on it, directly or through a mirror, or to the newest release when there is none. The other lists default to everything there is, and `validity` to `all`. An unknown release, puzzle, setup, or validity gives 400 naming the field. An unknown model name is ignored, because a link can outlive a model.

    ```json
    {"releases": ["1.3.2"],
     "options": {"providers": [{"name": "anthropic", "models": ["claude-opus-5-5"]}], "puzzles": ["2x2", "3x3"]},
     "models": [{"name": "claude-opus-5-5", "provider": "anthropic"}],
     "experiments": ["<id>"],
     "rows": [{"puzzle": "2x2", "metric": "precision", "direction": "higher", "tested": true,
               "cells": {"claude-opus-5-5": {"value": 0.41, "low": 0.30, "high": 0.53, "n": 60, "experiments": ["<id>"]}},
               "best": [{"model": "claude-opus-5-5", "against": "gpt-6-luna", "inputs_paired": 20, "p_value": 0.01, "p_holm": 0.02}],
               "worst": null}],
     "skipped": [{"id": "<id>", "error": "..."}]}
    ```

    1. The experiments read are those whose release is one of `releases` or a mirror of one (`is_mirror`), each once, read from git as the bundle reads them (Bundle 3). Each is re-validated from its raw records under its own release, never from its report CSV, because the paired model test needs one share per input. An experiment that cannot be scored is left out and listed in `skipped` with its error.
    2. `options` lists what the chosen releases hold before the `models`, `puzzles`, and `setups` filters: the providers in `PROVIDER_ORDER`, each with its AI models by name, and the puzzles in registry order. An AI model is its name and the provider of its entry in the experiment config. `models` is the AI models left after the filters, in the same order. `experiments` lists the ids read.
    3. `rows` holds one row per puzzle and metric, puzzles in registry order and metrics in the order of Benchmarks 3. A cell pools every attempt of that AI model and puzzle over the chosen releases, setups, and validity scope, with infrastructure failures left out as [definitions.md](../definitions.md#metrics) says. A rate cell has `value`, `low`, `high` (the bootstrap interval over inputs, `bootstrap_interval` in `src.evaluate.metrics`, with a key built from the puzzle, AI model, scope, and the chosen releases and setups, so it repeats), `n` (the number of attempts, as everywhere), and `inputs` (the inputs they cover, one per input set id and input id). The hallucination cell counts only the attempts that gave moves, so its `n` and `inputs` cover those attempts and the inputs that have one (`parsed_moves` is not empty, as `gave_moves` in `src.evaluate.metrics` decides). Any other cell has `value` and `n`, the attempts it covers. Every cell also has `experiments`: the ids of the experiments with at least one of the cell's attempts (after the release, setup, and validity filters, infrastructure failures included), in the order of the top-level `experiments`. `value` is `null` where the metric is `n/a`: mismatch detection under valid only, false mismatch under invalid only, hallucination when every attempt in the cell is a decision model's, and a group with no attempts. An AI model with no attempts on the puzzle has no cell. A precision cell is the precision of the one validity label in scope (`tp` and `tn` over the classified answers, `answer_class` in `src.evaluate.metrics`), and under both labels the balanced precision of [definitions.md](../definitions.md#metrics): the mean of the two precisions, `null` when either is, with a stratified bootstrap interval over inputs. The cost efficiency cell divides the mean cost per attempt by that same precision times the coverage, and is `null` when the product is 0 or `null`. Both are for display only; the report's balanced precision stays in the report.
    4. `direction` is `higher` for precision, the mismatch detection rate, and consistency, and `lower` for the rest, including the truncation, abstention, and format error rates. `best` lists the AI models with the best `value` in the row, every one tied at that value, and `worst` those with the worst. Either is `null` when the row has fewer than two cells with a value, or when every value in the row ties.
    5. `tested` is true for the eight rates: precision, hallucination, mismatch detection, false mismatch, malformed output, truncation, abstention, and format error. A hallucination cell that is `null` takes no part in the ranking, so it has no paired model test. For a tested row, each entry of `best` and `worst` carries the [paired model test](../definitions.md#metrics) against the first AI model past the tie in value order (`against`), with `inputs_paired`, `p_value`, `p_holm` (Holm-adjusted over the row's tests), and `agrees`: true when the paired inputs where the two AI models differ mostly show the named model better than `against` for `best`, and worse for `worst`, in the metric's direction. A tie gives false. The pooled value weighs inputs by their attempts and the sign test weighs each input once, so the two can disagree. A cell is coloured under a tier only when `agrees` is true. Each distinct pair is tested once, so with two cells `best` and `worst` name the same pair and share one test. An untested row has no test fields. For the hallucination rate, an input's share per AI model is over its attempts that gave moves, and an input with none for an AI model has no share for it and is unpaired. The maths reuses `sign_test` and `holm` from `src.evaluate.metrics` and lives in `ui/benchmarks.py`, outside the assessment.
    6. The server keeps answers in memory only, keyed by the query and the shas of `main` and of every `results/*` ref read, like the bundle (Bundle 4).
    7. Each experiment, once loaded and scored, is kept in memory as one entry per experiment id, stamped with the sha of its ref and the sha of `main`. The entry is replaced when either sha changes, and nothing else evicts it, so a new filter reuses it and memory is bounded by the number of experiments. The bundle build and the routes that load one experiment (`/api/experiments/<id>`, state, replay, attempt) read through this same entry, so an unchanged ref is read from git once, and `/api/experiments/<id>` takes its metrics from the entry's scored rows, so an unchanged ref is also validated once. A load that finishes after a newer entry was stored is not stored. A live experiment is read from its local ref, whose sha is in the stamp, so a commit on it replaces the entry.

Job names are `run:<model>`, `estimate`, `dry-run`, `evaluate`, and `commit`, plus the project jobs above. Every job runs with `cwd` at the root and the merged env from Inputs 10. The registry keys a job by experiment id and name, so a job that belongs to no experiment can use the id `""`.

## Polling

1. Snapshot. The page loads `GET /api/state/<id>` on load, and again every 1.5 seconds while any job of that experiment is alive. The poll that sees the last job end is the final one. With no job alive it loads once and stops.
2. Log. The page polls `GET /api/log?after=<seq>` every second while any job is alive and every 5 seconds otherwise.
3. In-progress attempts. For each model with a running `run:<model>` job, the page marks the first N attempts with no record, in the loop order of [run.md](run.md#outputs): input in release order, then setup, then attempt number. N is the model's `parallel` from the snapshot, 1 when it is missing. These are the attempts [`run --parallel N`](run.md) keeps in flight, so it is an inference, as `run` doesn't report them. It holds, except that near the end of a `--limit` run, and after a budget stop until the job ends, it can overcount by up to N−1. Each is marked in the plan and gets its own "sending…" block in the terminal. The Cube panel follows the first of them.

## Commit

The commit never touches the working tree, the index, or `HEAD`:

1. `git fetch origin main`, then `git fetch origin results/<id>`. The parent is `origin/results/<id>` if that fetch succeeds, else `origin/main`. [run](run.md#outputs) commits to the local branch `results/<id>` as it goes, so if that branch exists and the remote branch is missing or an ancestor of it, the parent is the local branch instead. If the local branch is an ancestor of the remote one, the preview moves it forward to the remote branch. The local branch is then "ahead" when the remote branch is missing or differs from it.
2. Before building the tree, `stale_files` from `src/run/branch.py` (see [run](run.md#outputs), Outputs 3) compares every `results/<id>/raw/*.jsonl` on the parent with the work tree. A work-tree file that does not start with the branch file's exact bytes gives 409 with the same message as `run`: `results/<id>/raw/<model>.jsonl on <ref> holds records this checkout lacks; bring the branch's results into the work tree first, after checking that no local records are uncommitted (for example: git restore --source=<ref> --worktree -- results/<id>)`. `<ref>` is the ref the files were read from: the local branch `results/<id>` when it exists, else `origin/results/<id>` (the UI names the parent it used, `origin/main` when the branch does not exist). The verb is `hold` for several files. It is `git restore`, not `git checkout`, so the real index stays untouched. Without it, the new tree would replace the branch's longer file with the shorter local one. A raw file gone from the work tree is not compared.
3. With `GIT_INDEX_FILE` set to a temporary file: `git read-tree <parent>`, then `git add -- results/<id>`, then `git write-tree`. Only that path is ever added (the config's copy is `results/<id>/experiment.toml`), with `--ignore-removal` so a file already on the branch is never dropped, and without the temporary copies `.experiment.toml.*.tmp`.
4. Preview: the files are `git diff --name-only <parent> <tree>`, and the diffstat is `git diff --stat <parent> <tree>`. No files, no branch on the remote, and no local commits ahead means 409 "nothing to commit".
5. Commit, in this order, so a failure at any step can be run again: `git commit-tree <tree> -p <parent> -m "Results: experiment <id>"`, then `git push origin <commit>:refs/heads/results/<id>`, and only after the push succeeds `git update-ref refs/heads/results/<id> <commit>`. With no files but a branch already on the remote, there is no new commit and the step goes straight to the pull request. With no files but local commits ahead, there is no new commit either: the step pushes the local branch, then goes to the pull request.
6. Pull request: if `gh pr view results/<id> --json url,state` finds one whose state is `OPEN`, return its URL. A closed or merged pull request doesn't count. With no files, nothing ahead, and an open pull request, 409 "nothing to commit". Else `gh pr create --base main --head results/<id> --title "Results: experiment <id>" --body "<body>"`. The body lists the release, puzzles, models, attempts, and a link to the report path. It carries no attribution line.
7. The `gh` binary is `$UI_GH` if set, else `gh`, so tests can stub it.

Every git and gh command is echoed to the terminal as a `commit` job.

## Page

Two parts: a left menu, fixed to the viewport height, and the page on the right. The router (`router.js`) reads the hash: `#/benchmarks`, `#/models`, `#/puzzles`, `#/puzzles/<puzzle>/inputs`, `#/experiments`, `#/experiments/<id>`, `#/new`, and `#/about`, each with `?release=<version>`, and any other filter, in the hash too, so a link or a reload opens the same view. An empty hash opens `#/experiments`. Each page is one file in `ui/static/pages/` with a `render(bundle, params)` function, and a page that needs more than the bundle loads it itself.

The page title and every block heading, such as a puzzle card's name or the New Experiment page's Puzzles, AI models, and Parameters, are 18px. The gap under the page title equals the page's 16px top padding.

Every text taken from a file ends with a small "source" link to that file on GitHub, at the commit sha of the ref it was read from, as `https://github.com/<owner>/<repo>/blob/<sha>/<path>`. With no GitHub base URL, there is no link. On the Puzzles page the sources are footnote markers instead.

Markdown is rendered by `markdown.js`, a small renderer for headings, paragraphs, numbered and bulleted lists, links, inline code, code blocks, emphasis, and tables. It escapes all HTML in the source first and allows only `http`, `https`, and relative links, so a file can never inject markup. A relative link points at the same file on GitHub.

### Left menu

1. A "New Experiment" button under the menu title. It opens `#/new` for the newest release.
2. Benchmarks, Models, Puzzles, Experiments, and About, with the current page highlighted.
3. The menu has no release select. Every page shows the newest release, unless the hash names another with `?release=`. Menu links and New Experiment never carry `?release=`, so they always lead back to the newest release. The Experiments page has its own release picker ([Experiments](#experiments)).
4. At the bottom of the menu, a theme switch with a ↻ button beside it. The theme switch is Light, Dark, and System, default System. System follows the browser's `prefers-color-scheme`. `theme.js` keeps the choice in `localStorage` under `theme`, inside try/catch, and loads in `<head>`, so the page never paints in the wrong theme.
5. Beside the menu title, a status dot. Its colour shows the server: grey while connecting, green when the server answers, red when it doesn't, and amber when it answers but the last GitHub fetch failed. Hovering or focusing the dot shows a styled tooltip panel, linked to the dot with `aria-describedby`, while the dot's own accessible label is "Status". The panel is short prose with up to three sentences, in this order. The server sentence is "The server is live.", "Connecting to the server.", or "The server is not reachable. Reconnecting." The GitHub sentence is "Data was fetched from GitHub on <time>.", "GitHub was not reached, so this shows data from <time>. Error: <error>.", "GitHub was not reached and there is no data yet. Error: <error>.", or "Nothing has been fetched yet." The release sentence is "Release <release>, the newest." when the page shows the newest release, or "Release <release>. The newest is <newest>." otherwise, and it is left out until a bundle is loaded. The panel text is set only when it changes, so the poll never closes an open panel. The log poll sets the server state and each bundle sets the fetch state.

### Cache and refresh

1. The page keeps each bundle in `localStorage` under `bundle:<release>`, and the release of the newest answer under `bundle:last` (the instant cached render uses it when the hash names no release), inside try/catch, so a blocked storage only loses the cache. A cached bundle with another `schema` is dropped.
2. On load, and on a release change, the page renders at once from the cached bundle if there is one, then requests `GET /api/bundle` and renders again when it answers. The server's answer always replaces the cache.
3. ↻ requests the bundle with `refresh=1`, and spins until the answer. It then redraws the current page even when the bundle is unchanged, so the page requests its own data again (for example, the Experiment page's detail and snapshot). Fields a page keeps across a redraw stay: New Experiment's form and About's bump and release note. Other unsaved input, such as a key being typed on Models, is cleared. A failed request keeps the cached view and shows the error under the menu.
4. When a job ends, the page requests the bundle again, so a pushed experiment appears.
5. The token changes on every server start, so a page loaded before a restart gets 403 "missing or wrong X-Token". When any bundle request fails that way, the menu shows "The server restarted, so this page is out of date. Reload the page." in place of the error. "Reload the page" is a link to the current view that reloads it. Other requests still show the plain error.

### Terminal

The foot terminal: a folded "Terminal" box with the job log from `GET /api/log` and a Clear button. It sits at the foot of the page, a sibling of `#main` and not inside the actions, and shows on the About page only. It is hidden on the others, New Experiment included. It shows every job's log, for all experiments and project jobs. The UI keeps collecting log lines while it is hidden, so the history is there when it is shown. The Experiment page has its own terminal ([Experiment](#experiment)), so this one is hidden there.

`router.js` keeps every log line it receives, at most 5,000 like the server, and exposes them as `UI.lines`, so a page can draw the history when it mounts.

### Benchmarks

One view that compares AI models across experiments, from `GET /api/benchmarks`. The page has its own selectors and ignores the menu's release.

1. Selectors, in one row that wraps, each a dropdown of checkboxes like the Experiments column picker, except Significance and Validity, which are selects:
   1. Releases: every release of the bundle. The default is the one the server chose, the response's `releases`. A pick stays in the hash even when it matches the default, because the default moves when experiments land.
   2. AI providers: from `options.providers`. All by default.
   3. AI models: those of the chosen providers. All by default.
   4. Puzzles: from `options.puzzles`. All by default.
   5. Setups: no model, descriptive, and prescriptive, pooled. All by default.
   6. Validity: all inputs, valid only, or invalid only. The default is all.
   7. Significance: All (no test), Weak (p < 0.10), Significant (p < 0.05), or Strong (p < 0.01). The default is Significant.
   8. Metrics: precision, hallucination rate, mismatch detection rate, false mismatch rate, malformed output rate, truncation rate, abstention rate, format error rate, consistency, latency per attempt, tokens per attempt, and cost efficiency. The default is the first three.

   Every choice that differs from its default is kept in the hash (`#/benchmarks?releases=…&providers=…&models=…&puzzles=…&setups=…&validity=…&sig=…&metrics=…`). Releases, AI providers, AI models, puzzles, setups, and validity send a new request. Significance and metrics only redraw.
2. Winners and losers: in each row, every `best` cell is green and every `worst` cell red. Under All, every `best` and `worst` is coloured. Under a tier, a tested row's cell is coloured only when its `p_holm` is below the tier's threshold and its `agrees` is true, and an untested row is never coloured, with the note "Consistency, latency, tokens, and cost have no significance test, so they are coloured only under All." when such a row is shown. Green and red are the same tokens in the charts and the table, and in both themes.
3. Bar charts come first: one small chart per puzzle and metric, in table order, laid out in a grid that wraps. Bars are horizontal: one row per AI model, grouped by provider in column order, with the short name on the left, written horizontally, and the value at the end of the bar. The short name is the AI model name without its first `-`-separated part (`claude-haiku-5-5` shows as `haiku-5-5`), and the full name is its tooltip. A rate's bar has a whisker for its bootstrap interval, and rates share a 0 to 100% axis. A bar is neutral unless it is the row's coloured winner or loser, and then its short name and value take the same colour, so a winner at 0% still shows. A model with no value has no bar. The chart title is the puzzle and the metric, and the metric is followed by an (i) icon: hovering or focusing it shows the metric's definition from `metric_definitions` (Bundle 6) in the shared `.tip-fixed` panel (placed below its source, or above it when it does not fit below and there is more room above, and closed by a mouse click on the icon), linked with `aria-describedby`, and the icon links to `metric_definitions.source`. A metric with no definition has no icon.
4. The table follows. The column headers have two levels: the provider, spanning its AI models, then each AI model by its short name, with the full name as its tooltip. The row headers have two levels: the puzzle, spanning its metrics, then each metric, with the same (i) icon as the chart titles. A rate cell reads `41.0%`, consistency two decimals, latency seconds with one decimal, tokens grouped digits, and cost `$0.00`. `n/a` where `value` is `null`, and empty where there is no cell. A coloured cell's tooltip names the test: "Better than <model>: p = 0.004 (Holm 0.008), 20 inputs paired." Every rate cell's tooltip shows its interval, `n`, and the number of inputs. A cell's text is a button that opens a panel under the cell (above it when it does not fit below and there is more room above), titled with the puzzle, metric, AI model, the cell's `n`, and the number of experiments (`2x2 · Precision · claude-opus-5-5: n=114, 1 experiment`), that lists every id in the cell's `experiments` as a link to `#/experiments/<id>`. The panel follows its cell in tab order, and the cell's tooltip is on the button. One panel is open at a time. A second click on the same cell, a click outside, focus leaving the cell, Esc (which returns the focus to the cell), a scroll outside the panel, and leaving the page close it. Cube panel: the Cube block of the Experiment page. The 3D view (`cubeIso`) is on the left and the net (`cubeNet`) of the same frame is on the right, always both. Below them are the move list, with the current move highlighted and an impossible move in the hallucination colour, and then the outcome, the input id, the setup, and the attempt number. The page never holds the move group: it draws the `frames` of `GET /api/replay/<id>`.

1. Controls: Play/Pause, Step back, Step forward, and a speed select of 0.5x, 1x, 2x, and 4x, where 1x is 300 ms per move. A frame that follows a move highlights the face named by the move's first letter. Play at the last frame starts again from the first.
   Turn animation: when the panel steps forward by one frame, by Play or Step forward, and the move is a face turn (`U`, `R`, `F`, `D`, `L`, or `B`, plain, `'`, or `2`) that the replay applied, the 3D view shows the turn with `cubeIsoTurn` before it shows the new frame. The outer layer of the named face turns about that face's axis, a quarter turn for `X` and `X'` in the direction the engine moves the stickers and a half turn for `X2`, using the colours of the frame before the move, while the net stays on that frame until the turn ends. It runs on `requestAnimationFrame`, eased in and out, for one playback interval at the current speed less a hold of 40 ms (at most a fifth of the interval). Stepping back, a move the replay stopped at, a move that is not a face turn, a new replay, and a click on an arc show the frame at once. Any redraw ends a turn in progress.
2. Live mode is on by default. When a record lands in a snapshot taken during a run, the panel loads its replay and plays it. Records already there when the experiment loads are not replayed. The queue holds one record: while a replay plays, or during the pause after it, only the newest unplayed record of the followed AI model waits, and an older waiting one is dropped. When the playback ends, the panel pauses for about 600 ms and then plays the queued record, so a replay is never cut off by a newer record. While an attempt is in flight with no newer record, the panel shows that attempt's input and a slow pulse, with the text "waiting for <model>". The in-flight attempt is the page's own inference ([Polling](#polling)). When no job of the followed AI model is running, the waiting state clears and the panel shows the last replay, or stays empty. Changing the model, turning Live off, or clicking an arc drops the queue and any load still in flight. A replay error shows in the panel's own line, not in the form message. With more than one AI model, a model select picks which one the panel follows.
3. Clicking an arc that has a record replays that attempt and turns Live off. The Live toggle turns it back on.
4. A puzzle that is not an `NxN` cube, or one with no engine in the registry, shows "no drawing for <puzzle>" or a single frame.
5. With `prefers-reduced-motion`, the pulse, the face highlight flash, and the turn animation are off, and playback only steps. The thicker outline on the turned face stays, because it is static.

Cube net: a state is `6·n·n` characters over `URFDLB`, faces in that order, each face row-major. The net puts U above F, L, F, R, and B in a row, and D below F. Sticker colours: U white, R red, F green, D yellow, L orange, B blue. Cube 3D view: `cubeIso(state, n, highlightFace)` draws the U face on top, F front-left, and R front-right, each as an `n × n` grid of parallelograms in the net's colours. Sticker order follows the state's reading convention ([cube.md](cube.md)): U is read from above with B at the top, so its first row is the back row, and F and R are read with U at the top, with R's first column next to F. Cube turn view: `cubeIsoTurn(state, n, move, p)` draws `state` with `move` done for the eased progress `p` from 0 to 1, in the same camera and with the same geometry and colours as `cubeIso`. It draws every sticker of all six faces as a 3D quad. A sticker is in the turning layer when its centre is at least `n - 1` along the face's axis, in the engine's units, and a finished turn puts each sticker where `_moves` in `src/puzzles/cube.py` does. Quads facing away from the viewer are dropped, and two dark cut faces (`#1b1f27`), one on the turning layer and one on the rest, close the solid so the inside never shows. The turning layer and the rest are convex and the cut plane separates them, so the one on the viewer's side of that plane is drawn last, and the quads inside each are depth-sorted by their centres. A string that is not a face turn gives the plain `cubeIso`. `cubeIsoTurn` holds no highlight outline: the panel draws the frame, with its outline, when the turn ends.

## How to test

`tests/test_ui.py` and `tests/test_ui_bundle.py`, with temporary folders, a temporary repo with a bare remote as `origin`, the `fake` provider, and no network. The server is started on port 0 in a thread.

1. Keys: file modes, no backup copy, a real env var winning, an empty env var losing to a saved key, and only the last 4 characters in any `GET` body. Every secrets route needs the token.
2. The bundle marks a catalogue model with no price, and a model with no key, as disabled, with the reasons above, and reads the catalogue and prices from `main`: a change in the work tree that is not committed and pushed does not show.
3. Items 6 to 8 of the API for each of `created`, `unchanged`, `budget_updated`, and 409, with the config read from the branch. On 409 no job starts. No call writes any file under `config/experiments/`, and the config on each job's stdin loads with `parse_experiment_config` and holds `puzzles`. A config without `puzzles` compares equal to the same choice made on the page. A branch whose results are not in the work tree gives 409 and starts no job.
4. A POST, `GET /api/bundle`, or `GET /api/secrets` without the token gets 403, whatever its `Host`. `GET /static/../secrets/anthropic.json` and `GET /secrets/anthropic.json` get 404.
   1. In the default mode, `8.8.8.8:<port>`, `10.1.2.3:<port>`, `localhost:<port>`, `[::1]:<port>`, `10.0.0.11` with no port, and `10.0.0.11:443` are accepted. `evil.example`, `localhost` with no port or a wrong port, and `aiohr.dorland.keenetic.pro` are refused without `--allow-host`. With `--allow-host`, that name is accepted with no port, with `:443`, with `:80`, in any case, and with a trailing dot, and the 403 for another name echoes the header and names the option.
   2. In the default mode, `verify_request` accepts the peers `8.8.8.8` and `172.16.0.1`, and `handle_request` does not refuse a non-loopback peer. `is_loopback("::ffff:127.0.0.1")` is true and `is_loopback("not-an-ip")` is false.
   3. The start-up text holds the "Open to every client" line and the allowed host names.
   4. With `--no-lan`, a `10.0.0.5` peer and an `evil.example` `Host` are refused, and loopback is accepted.
5. The log keeps only the newest lines at the cap, and `after` returns the newer ones.
6. A full run through the API on a one-puzzle release: records appear in `/api/state` from the local branch while the run is alive, the experiment shows in the bundle as `pushed: false`, then as pushed once the run exits, the snapshot has no `in_progress`, and the run job ends `done`.
7. Run is refused while evaluate is alive, and evaluate while a run is.
8. Stop, and stop on server shutdown: a server given SIGTERM leaves no run alive.
9. Commit against a temporary bare remote, with `UI_GH` pointing at a stub script: the branch exists on the remote with only `results/<id>` changed, the working tree and `HEAD` are unchanged, and a second commit with no changes gives 409. Local commits ahead of the remote with an empty diff are still pushed.
10. A failed push and a failed `gh pr create` can each be run again, and only an open pull request counts.
11. Commit is refused when the report is older than a raw file, and with 409 when a work-tree raw file is shorter than the branch's.
12. Project jobs: the argv of each job, the 409 on `main` and on a detached HEAD, the blank-note 400, mutating jobs refused while any job runs, the `/api/project` shape, and push against a temporary bare remote with a stub `gh`.
13. Replay: the frames equal successive `apply_move` calls, an impossible move stops the replay at its index, malformed output gives one frame and no moves, a missing record gives 404, a bad query field gives 400 naming it, and every file named under Files is served from `/static/` while other unknown static paths give 404.
14. Bundle from refs only: a results folder in the work tree with no branch does not show, and a branch pushed to the bare remote shows after `refresh=1`. A branch with no `experiment.toml` is left out.
15. Bundle memory: the same ref shas return the same object without rebuilding, and a ref that moves gives a new bundle. The server writes no file anywhere while it serves every read route.
16. Rows and metrics: three rows per experiment, AI model, and puzzle, one per validity scope, and the `valid` and `invalid` rows' attempts add up to the `all` row's. `summary_rows` from a CSV equal those `compute` gives on the same records. With a report CSV on the branch, the rates equal the CSV's pooled numbers and `metrics_source` is `report`. Without one, they equal `src.evaluate.metrics.compute` on the same records and `metrics_source` is `computed`. Infrastructure failures change no rate. A branch with a broken config gives one row with `error`, and the other rows still build.
17. Model matching: an experiment whose entry has the catalogue's `provider` and `api_model_id` under another name is listed under that catalogue model, and one with the catalogue's name but another `api_model_id` gets `differs_from_catalogue`.
18. Impossible moves: fixture records with known impossible moves give the expected moves, counts, models, and experiment ids, and legal moves never appear.
19. Source links carry the sha of the ref read, for both `https://` and `git@github.com:` remotes, and there are none with no `origin`.
20. A failed fetch (the remote removed) still builds a bundle from the old refs, with `fetch_error` set.
21. `default_id`: names, the three-item cap, the character rule, and the time format, and the result passes `EXPERIMENT_ID_PATTERN`.
22. `/api/branches` lists local-only and remote-only branches, and `/api/experiment/<id>/config` reads the local branch before the remote one.
23. `/api/inputs` returns the release's inputs of one puzzle in order, and 400 for an unknown puzzle.
24. Outcome colours are in the page scripts and are not tested here. The colour table is one object, in one file.
    The terminal's pattern for `run`'s progress line is checked against a real `Progress.plain_line` in `tests/test_ui_js.py`, so a change to either breaks the test. The layout, the plan tree, and the terminal are checked by hand with screenshots in both themes at 900 and 1500 pixels wide.
25. The page scripts pass `node --check`. A node script, `tests/js/markdown.test.mjs`, run by a pytest test when `node` is found and skipped otherwise, checks that `markdown.js` escapes `<script>` and HTML attributes, drops `javascript:` links, and renders a table, a numbered list, and a link.
26. The cube drawing is checked by hand with `node --check` on both scripts and a throwaway node script that loads `cube.js`, draws scrambled states from a release, and compares every sticker of `cubeIso` with `cubeNet`, and the edges where U, F, and R meet.
27. `kind`: the catalogue and `model_entries` carry it (`null` when unset), the form copies it from the catalogue into the experiment config, and `differs_from_catalogue` ignores it.
28. Run and its branch: `POST /api/run` answers once its jobs start, and the log's `branch` job says "creating results/<id>…" and then "results/<id> created", or "results/<id> exists: resuming" on a resume; a run that stops before its first commit still answers 200, and the `branch` job logs a stderr line with its last stderr line (prices file moved away); and Run, Estimate, and Dry run give 409 when `releases/<release>/` is missing from the work tree.
29. Parallel requests: `POST /api/run` with `parallel: 3` starts each run job with `--parallel 3`, and without `parallel` adds no flag. 0, 17, `true`, `"4"`, and a fraction give 400 naming `parallel`. The config on stdin is byte-identical with and without it. The snapshot's `parallel` carries each running job's value, 1 for a job not started with it. A second node script, `tests/js/progress.test.mjs`, checks that the in-flight inference is the first N attempts without a record, in loop order.
30. Estimate table: a test in `tests/test_ui_js.py` runs `run --estimate` on a temporary release and checks with `node` that the page's `ESTIMATE_MODEL` pattern matches every line but the last, and `ESTIMATE_TOTAL` only the last.
31. Benchmarks: the pooled rates equal `rates` from `src.evaluate.metrics` on the same attempt rows. Two experiments on one release, and an experiment on a mirror, are each read once. Inputs pair on input set id and input id, so the same input id under another input set never pairs. A row with one cell has no `best` or `worst`, a row that ties throughout gives `null`, models tied at the top or bottom are all listed, each tested against the first model past the tie, and with two cells `best` and `worst` share one test. `p_value` equals `sign_test` on the discordant inputs, and `p_holm` equals `holm` over the row's tests. The filters narrow `models` but not `options`. An unknown release, puzzle, setup, or validity gives 400 naming the field. The same shas return the cached answer. A moved ref of an existing experiment gives a new answer: the experiment is read and scored again, and the stale scored entry is not used, with one scored entry left for it. The scored cache holds one entry per experiment id, however many experiments there are, and replaces it when the ref sha or the main sha changes. A node script, `tests/js/benchmarks.test.mjs`, run by a pytest test, checks the colouring gate (under a tier, colour only when `p_holm` is below the threshold and `agrees` is true; under All, always colour best and worst; an untested row never under a tier) and that `models=` names matching none of the chosen providers' AI models mean no model filter.
32. Dollar amounts: `UI.usd` in `router.js` is the one money formatter. Each page passes the options that reproduce what it printed before: Experiments, Benchmarks, and the experiment page summary (`expmetrics.js`) `{ fixed: 2 }` (n/a for a non-number on Experiments), Models the browser's own locale (`locale: "browser"`) with 2 to 4 places, and New Experiment en-GB with 2 places (4 below one) and inf, nan, and amounts below 0.00005 as printed. A node script, `tests/js/usd.test.mjs`, run by a pytest test, checks each page's options against its former output on a spread of values. It loads `router.js` through the DOM stub in `tests/js/load_router.mjs`.
33. Pickers: a node script, `tests/js/pickers.test.mjs`, run by a pytest test, checks that `UI.dropdown` builds a labelled select with the given options and value and calls its handler with the chosen value, and that `UI.checkPicker` shows its summary for none, one, several, and all selected, disables the last ticked box, reports the ticked values in option order, and opens again on the toggled box once, consuming the key.
